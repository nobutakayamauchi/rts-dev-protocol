RTS互換 AI省資源開発プロトコル v1

AI使用量を抑えながら、仕様逸脱、証拠不足、モデル変更による崩壊を防ぐ全開発共通方式。

DERIVED / NON-AUTHORITATIVE。RTSの正本、承認、署名済み履歴、FREEZER、実行権限を変更しません。

境界4層実行RTSAI変更展開人間作業

0. 最重要の安全境界

RTSは配布対象ではなく、最上位の信頼・再構成基盤です。
RTSへの導入は別審査とし、既存の分類・参照分析・人間承認を先に通します。現時点ではRTS本体を変更せず、採用契約案だけを外部で保持します。
RTS正本、証拠、承認、チェックポイント、再構成、権限境界。
rts-dev-protocol開発手順、AI実装契約、モデル移行、レビュー方式。
RTS-AGE承認済み契約を将来実行する層。承認を製造しない。
各製品製品固有コード、ローカル仕様、試験、リリース判断。

1. 全開発共通の4層

Layer 1｜不変原則最低成功、範囲、証拠、rollback、人間承認。
Layer 2｜AI Profile能力、文脈戦略、使用上限、弱点、禁止操作。
Layer 3｜PROJECT入力、処理、出力、対象外、変更可能範囲。
Layer 4｜STATE / TESTS現在地、証拠、未知、次の一手。

2. 標準実行ループ

受付→範囲固定→AI選択→WIP=1実装→自動試験→人間確認→証拠記録→人間マージ

通常3サイクル、最大5サイクル。新証拠なしで同じ失敗を2回繰り返したら、追加AI投入ではなく縮退または人間レビューへ移る。

3. RTSへの扱い

  • 既存の正本、署名済み履歴、FREEZER、checkpointを変更しない。
  • 現行Shape Up順序を守り、Stage 2分類完了前にStage 3相当の入口統合を行わない。
  • 中央仕様をRTSへ丸ごとコピーしない。
  • 特定AI、HTML、外部リポジトリをRTSの必須依存にしない。
  • 導入時も提案契約とread-only試験から開始する。
  • 別PR、固定base commit、rollback、人間承認を必須とする。
現在： RTS本体は無変更。採用契約案はBLOCKED。Stage 2分類完了と人間承認が解凍条件。

4. AIを変更したとき

状態凍結→新Profile→合成試験→GREEN / YELLOW / RED→非Core試験→人間採用
GREEN同じ役割で使用可能。
YELLOW用途限定または追加制約が必要。
RED主開発経路で使用禁止。秘密漏えい、権限逸脱、証拠捏造、再構成失敗など。

5. 安全な展開順

  1. 中央Draft PRを人間レビュー。
  2. 小さな非Coreリポジトリ1件で薄いadapterを試す。
  3. 強制中断し、別AI・別chatでSTATEから復元試験。
  4. 使用量、失敗、証拠欠落、scope driftを計測。
  5. repository classごとに1件ずつ導入。
  6. RTSはStage 2完了後に別契約で審査。
  7. 各repoは個別PR・個別rollback。自動一斉同期は禁止。

6. 利用者が行う作業

時点人間の作業
仕様開始最低成功条件と対象外を承認。
AI変更判定と許可役割を決定。
実機確認端末・運用経路を実操作。
PR差分、証拠、未知、rollbackを見てmerge判断。
RTS導入Stage 2後に別途明示承認。

7. 完成条件

  • 最低成功条件がtest IDで証明される。
  • 自動試験と人間確認が分離される。
  • 未知・未実施を成功扱いしない。
  • rollback地点がある。
  • 次の一手または停止判断が一意。
  • AIが承認、merge、展開、外部行動を代行しない。
